## Hysteria follow-up

Later Windows tests found intermittent failures on the MSK UDP relays too:
DE failed twice via MSK while direct DE passed; FI and NL initially passed via
MSK and failed on the following run. A real native Hysteria client on FI passed
all three MSK relays at another instant, confirming that node service status
alone did not explain the client's failure.

Switched `vpn.de.hy2_addr` to `147.45.63.107:443` and
`vpn.de.hy2_obfs.addr` to `147.45.63.107:24443`; switched
`vpn.hysteria2.addr` to `78.17.1.122:443` and its `obfs.addr` to
`78.17.1.122:24443`. NL remains through MSK by explicit request. Auth, pins,
obfuscation passwords, and LTE XHTTP configuration were preserved. Atomic
updates have timestamped backups.

Actual subscription HTTP 200 returned DE and FI Hysteria on their direct
addresses and NL on MSK UDP/24447. The Windows Ghostly Xray binary, running
temporary child configs from that response, successfully performed HTTPS,
1 MiB download, 256 KiB upload and SOCKS UDP DNS for both direct DE and FI.
Existing application processes were not stopped. These tests validate the
current PC path, not every carrier/network.

During observation MSK load fell to 0.00/0.04/0.10; malformed-packet guard
counters stayed at zero. A ten-second sample counted 199 TCP retransmissions
and 141 TCP timeouts, with zero new SYN cookies, listen overflows or listen
drops. One eight-second sample saw 532 client UDP packets forwarded to nodes
and 685 return packets sent to clients. Neither sample proves absence of an
upstream attack or establishes TSPU attribution. MSK/NL instability is unresolved.

## Recovery and scheduled return

Around 02:43 Yekaterinburg all 24 TLS probes from FI/DE/NL passed; real Windows
NL Vision and NL Hysteria profiles through MSK passed HTTPS, download, upload
and UDP DNS. The user supplied a FirstVDS representative's DDoS confirmation.
All three countries were briefly restored through MSK at the user's request;
all six Vision/Hysteria Windows tests passed. The user then supplied the
provider's warning that filtering was temporary and cancelled the restoration.
FI/DE were returned to direct TCP/Hysteria; NL remains through MSK.

At the user's explicit request, installed and enabled a single persistent
systemd timer on FI, scheduled for 2026-11-27 05:22:48 UTC (10:22:48
Asia/Yekaterinburg), approximately 7.5 hours after scheduling. It restores all
three countries and Hysteria through MSK without an interactive session or a
health gate. Live timer state and NTP synchronization were verified. Script
checks on an isolated fixture verified backup contents, ownership/mode handling,
preservation of other settings, dry-run behavior and idempotence. Production
remained FI/DE direct and NL via MSK when the timer was enabled.

Verified generated links and Xray arrays, then HTTP 200 from the actual local
subscription endpoint using an existing exempt subscription/device identity:
the returned Xray profiles contain FI direct, DE direct, and NL via MSK. This is
an HTTP delivery check, not an end-client tunnel transfer test.

Direct TLS probes found two neighbour targets failing: DE Vision `2.26.252.6`
(`pybattle.beer`) and NL XHTTP `2.26.252.27` (`ger01.deflink.net`). On the matching
nodes, marked those upstream servers `down` in `ghostly-reality-dest.conf` so
the existing local TLS backup on port 8475 is selected without waiting for a
failed connection. Backups made, nginx syntax checked, graceful reload used.
Other neighbours remain configured. Local backup certificates are self-signed
and change the unauthenticated probe response; authenticated REALITY clients
do not use ordinary certificate trust validation for this response.

Observed intermittent TCP and TLS timeouts from Europe to MSK, with low MSK
resource usage and no demonstrated SYN queue saturation. Failed neighbours do
not explain TCP connect timeouts before ClientHello. DDoS, TSPU filtering and
provider mitigation remain unproven; no claim of full client recovery.
